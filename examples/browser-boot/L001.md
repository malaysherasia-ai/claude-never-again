# L001 — a syntax checker cannot see a TDZ error

**Filed:** 2026-09-12 · **Scope:** web · **Form:** hook (warn)

## Symptom

Every button on the page was dead. Tabs, header strip, the lot — nothing
responded to a click. No visible error, no failed request.

## Cause

A `let` declaration was used by a function that ran before the declaration was
reached. That is a temporal dead zone ReferenceError, and it aborts the whole
script at boot, so every event listener registered after it silently never
attached.

`node --check` passed. It only parses. The error is a runtime one.

## Rule

Boot every build in a real browser before shipping. A syntax check is not a
boot.

## Why this became a hook

The check is mechanical and takes one sentence: *before committing, fail if the
page does not boot.* Nothing about it needs judgement, so leaving it as a note
in `LESSONS.md` would have been paying tokens forever for something a script
can hold.

## What the hook does

`L001.sh` is five lines: `ID`, `RULE`, `TRIGGER`, and a `source` of the
verify engine, `na-verify.sh`, that the installer puts next to it. Everything
else comes from the lesson's `verify` block in `state.json`
(`state.snippet.json` here):

```json
"verify": {
  "run":   "node scripts/boot-check.mjs",
  "watch": [".html", ".css", ".js", ".mjs"],
  "skip":  ["scripts"]
}
```

Watched files come from git, so anything in `.gitignore` (screenshots, audit
output) is never counted. `skip` is for tracked paths the boot does not load;
it matches from the root, so `scripts` leaves `src/scripts/` watched.

1. Compares every watched file against `.claude/never-again/verified/L001`,
   a manifest of sha256 hashes written the last time the boot passed. If
   nothing differs, the commit goes through and the hook says nothing.
2. If something differs, **the hook runs the boot itself**. A passing boot
   rewrites the manifest and the commit goes through, still silently. Expect
   this to take as long as your boot check does, which is why the settings
   entry carries `"timeout": 180`.
3. Only if the boot fails does the hook fire, naming the failure. In warn
   mode that is a permission prompt; in block mode the commit is refused.

The same script runs from git's own pre-commit hook, so a commit made from a
terminal, another agent, or a different tool gets the same treatment. To boot
by hand and record it: `bash .claude/hooks/na/L001.sh --run`.

Change `run` and the tool is no longer web-only: `npm test --silent`,
`pytest -q`, `go build ./...`, anything that exits non-zero when it should.

## Why it runs the boot instead of asking whether you did

The first version tested a stamp file and asked "was the page booted since the
last edit?". Two things were wrong with that.

It fired on commands like `bash mark-boot.sh && git commit`, every time. A
`PreToolUse` hook sees the repository as it is *before* the tool call runs, so
the stamp was always stale at the moment the hook looked. Six of the first nine
fires in a real project were this, and each one was approved within seconds
because the person could see the boot was about to run anyway. A prompt that
is always approved teaches everyone to approve prompts.

And it made the hook depend on a person remembering a separate command, which
is the failure this whole tool is meant to remove.

## What the boot check requires

`scripts/boot-check.mjs` is yours to supply. The reference implementation in
the site that launched this tool drives headless Chrome over the DevTools
Protocol using the global `WebSocket`, so it needs **Node 22+**. On anything
older, supply a boot check of your own: any command that loads the page and
exits non-zero when it is broken will do.

Whatever you use, it must genuinely fail on a broken page. A hook whose
command can never fail is worse than no hook, because it proves nothing.

## The line in LESSONS.md

```
- [web] [hook] Boot the build in a real browser, not `node --check` — when: before commit (L001)
```

## Why it records hashes, not a timestamp

A stamp that only records *when* the boot ran fires on a file restored from a
backup, a checkout of the same revision, or a formatter rewriting a file
byte-for-byte: the mtime moved, the bytes did not. The manifest records one
sha256 per tracked file, so a file whose bytes are unchanged is silent, which
is the whole point.
