# L005: a hook's exit code is not its verdict

**Filed:** 2026-09-23, from the sixth field run (a client site built with
Antigravity). Form: rule line.

**Symptom.** The first real catch in the field, a warn-mode hook finding
staging URLs in a homepage schema during a git commit, was recorded in
`fires.log` as a fire and in `calls.log` as a clean commit. `na` counted
one fire; the line that says whether the agent called the hook said
nothing had happened.

**Cause.** The dispatcher decided the calls.log verdict under git from the
hook's exit code alone. A warn under git prints its reason and exits 0 so
the commit can go ahead, which is the design; only block exits 1. So
every warn fire under git looked clean. The Claude Code branch already
took what the hook printed as the verdict; the git branch did not.

**Rule.** A hook's exit code says whether to stop the command, nothing
more. When a runner records what hooks did, the evidence is what they
printed, on every runner alike.

**Fix.** The dispatcher captures each hook's output under git, prints it
on, and marks the call fired when any hook had something to say, the
same test the Claude Code branch uses. Two tests: a warned git commit is
a fired call, a quiet one is clean.

**What would have gone red:** nothing. The test for the git side checked
`fires.log` and the exit code, never `calls.log`.
