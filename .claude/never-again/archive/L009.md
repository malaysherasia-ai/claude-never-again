# L009: a log that hooks write is appended, and decided from a fresh read

**Filed:** 2026-09-24, from the code review of PR #33 (the failure
record). Form: rule line.

**Symptom.** None in the field yet. The review found it by reading:
`_append_failure` read the whole of `failures.log`, added a line and
rewrote the file, and `cmd_passed` removed the open mark from the rows it
had read before writing its own line.

**Cause.** Claude Code runs tool calls in parallel, so two after-tool
hooks can be in flight at once. Two read-modify-write cycles interleave:
the second writer's view lacks the first writer's line and drops it. A
decision taken from the pre-write view (nothing is open, remove the mark)
can be wrong by the time the write lands, and a failure that another call
had just recorded loses its mark, so its later pass costs nothing and
records nothing.

**Rule.** A log that hooks write is appended one line at a time, never
rewritten from a hook's view of it; a decision about the log's state
(a mark, a count) is taken from a read made after the hook's own write.
Rewriting is for commands a person runs, once, on a quiet file.

**Fix.** `_append_failure` opens the file in append mode and writes one
line. Trimming happens in `_failed` only when the file has grown past
twice the keep count. `_passed` re-reads the file after writing before
deciding whether the open mark goes.

**Not yet applied to:** `fires.log`, whose settle-and-rewrite path dates
from 0.2 and runs from the same after-tool hook. It has not been seen to
lose a line; the same rule applies and it is the next place to look.
